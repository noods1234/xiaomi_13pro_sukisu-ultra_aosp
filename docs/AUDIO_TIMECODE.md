# OIW-ROM Audio and Timecode

## 1. Audio sources

| Source | Status | Notes |
|---|---|---|
| Internal mic (`MediaRecorder.AudioSource.CAMCORDER`/`MIC`) | Implemented | Default fallback, lowest fidelity |
| USB audio interface (UAC1/UAC2 class-compliant) | Implemented | Via `AudioManager`/`AudioDeviceInfo.TYPE_USB_DEVICE`, standard Android USB-audio class support — requires the interface to be class-compliant; not all cheap "USB mic" hardware is |
| USB-C mic (integrated, no interface) | Implemented | Same USB audio device path as above |
| TRRS adapter | Unconfirmed on this device | Depends on whether the USB-C port's analog-audio-accessory mode is implemented by this SoC/board; test directly |
| Bluetooth (A2DP/LE Audio) | **Explicitly excluded for capture** (monitoring/headphone use only) | Variable, often 100ms+, non-deterministic codec latency — unacceptable for sync-critical audio (`assumptions.md` C-4) |
| External recorder (sync via slate/marker only, no direct audio ingest) | Implemented (workflow, not data path) | See §3 Tier 3 |

## 2. Audio controls

Gain (via `AudioRecord` + software gain stage where hardware gain isn't exposed), sample rate (44.1/48kHz, device-
dependent max queried at runtime), bit depth (16-bit guaranteed; 24/32-bit float only if
`AudioFormat.ENCODING_PCM_FLOAT`/24-bit is reported supported for the selected source — checked, not assumed),
mono/stereo, real-time meters (peak+RMS), clipping warning (sample-value clip count), headphone monitoring (if a
wired/USB headphone path is available; Bluetooth monitoring allowed here since it's not the record path), a manual
A/V sync-offset calibration (clap-test workflow, see §3).

## 3. Timecode tiers

| Tier | Mechanism | Accuracy | Status |
|---|---|---|---|
| 1 | System wall-clock timestamp embedded in filename + sidecar | Device-clock accuracy (NTP-synced if network available) | Implemented |
| 2 | Monotonic clock (`SystemClock.elapsedRealtimeNanos()`) sampled at first video frame and first audio buffer, delta recorded in sidecar as `av_sync_offset_ns` | Sub-frame, but only useful *within* a single clip, not across devices | Implemented |
| 3 | Manual slate metadata (typed scene/take + an on-screen "clap" visual flash + simultaneous audio blip generated by the app) for manual sync-by-eye/ear in post | Frame-accurate if user claps in sync with the flash | Implemented |
| 4 | Audio LTC (SMPTE Linear Timecode) detection on an audio input channel | Frame-accurate, standard cross-device sync | **Not implemented** — needs an LTC decoder (freewheeling PLL over the audio samples); documented as a concrete follow-up (implementation is a well-understood DSP problem, not blocked by hardware, just not built in this pass) |
| 5 | External timecode device integration (e.g., Tentacle Sync-class hardware via audio LTC input, tier 4's decoder, or a USB/BLE protocol if the device exposes one) | Frame-accurate, multi-camera | **Not implemented**, depends on Tier 4 first |

## 4. Clap/sync markers

The in-app slate screen's "mark" action writes a precise `SystemClock.elapsedRealtimeNanos()`-stamped sidecar event
(`slate_markers: [{ "type": "clap", "ts_ns": ... }]`) in addition to the audio-visual clap cue, so post-production sync
software has a numeric anchor even if the visual/audio clap is imperfect.

## 5. Latency tests

`docs/TEST_PLAN.md` §Audio Tests defines a round-trip latency measurement: play a known click through the device
speaker while simultaneously recording via the selected audio source, measure the delay between the emitted click and
its captured waveform peak. Repeated across internal mic, USB audio, to catch source-dependent latency differences
before they surprise a shoot.

## 6. Long-take drift

For Tier 1/2, sidecar records both the wall-clock start time and the monotonic-clock delta so any drift between
audio and video internal clocks (rare, but possible on long takes if the two paths use different internal clock
sources) can be detected in post by comparing expected vs. actual sample count against elapsed monotonic time.
